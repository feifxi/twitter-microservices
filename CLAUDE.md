# Claude Instructions — twitter-microservices

## Code Review / Verification Protocol

When asked to review, verify, or audit any service or the whole backend:

1. **Read every file first, report second.** Read all files in scope before surfacing any finding —
   no incremental passes. Scope includes: `cmd/main.go`, all `internal/**/*.go`, all `*_test.go`
   (including integration tests with `//go:build integration`).
2. **Use `go vet -tags integration` as the final check**, not `go build`. `go build` silently skips
   test files; `go vet` catches interface mismatches and compile errors in stubs.
3. **One pass, then fix.** Collect every issue in a single list before touching any code.
4. **Classify every issue:**
   - **Bug** — logic error, nil panic, wrong argument, interface mismatch
   - **Dead code** — unused func/method, stale import, orphaned package
   - **Inconsistency** — field present in one response type but absent in a parallel one
   - **Test gap** — stub that doesn't satisfy the current interface, stale method signature

## Service Layout

Every Go service follows this structure — no exceptions:

```
cmd/server/main.go           ← wiring only, no logic
internal/server/server.go    ← Server struct, routes(), Handler(), Start()
internal/server/handler_*.go ← thin HTTP handlers (bind → call service → respond)
internal/server/types.go     ← ALL request/response structs and their constructors
internal/server/grpc.go      ← gRPC handlers (where applicable)
internal/{domain}/service.go ← ALL business logic
db/sqlc/                     ← generated by sqlc, never hand-edit
migrations/                  ← golang-migrate SQL files
```

**Request/response types always in `types.go`.** Never inline anonymous structs in handlers,
never scatter structs across handler files. Constructor functions (`newXxxResponse`) live there too.

## Error Handling

The codebase uses a unified `httperr` package (replaced the old `apierr`/`domainerr` split).

```go
// In handlers — use httperr helpers directly:
httperr.Handle(c, err, s.log)      // maps known errors to status codes
httperr.BadRequest(c, "CODE", "message")
httperr.Validation(c, err)         // for ShouldBindJSON errors
httperr.Internal(c)                // only for cases with no error variable (e.g. SSE flusher)
httperr.Forbidden(c, "message")
httperr.NotFound(c, "message")

// In services — return sentinel errors from httperr:
return httperr.ErrNotFound
return httperr.ErrForbidden
return httperr.New(http.StatusConflict, "CODE", "message")
```

DB errors are mapped with `pgxutil.MapErr(err)`:
- `pgx.ErrNoRows` → `httperr.ErrNotFound`
- unique constraint → `httperr` conflict error

**Always wrap store/querier calls:** `return pgxutil.MapErr(err)` — applies inside `ExecTx`
callbacks too.

## Handler Pattern

```go
func (s *Server) handleCreateTweet(c *gin.Context) {
    claims := auth.MustClaimsFrom(c)          // panics if unset — OK on protected routes

    var req tweetBodyRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        httperr.Validation(c, err)
        return
    }

    result, err := s.tweet.Create(c.Request.Context(), claims.Sub, req.Body)
    if err != nil {
        httperr.Handle(c, err, s.log)
        return
    }

    c.JSON(http.StatusCreated, newTweetResponse(result))
}
```

## ExecTx + Outbox Pattern

```go
var result db.Tweet
if err := s.store.ExecTx(ctx, func(q db.Querier) error {
    var err error
    result, err = q.CreateTweet(ctx, params)
    if err != nil {
        return pgxutil.MapErr(err)
    }
    // Count increments are best-effort — Warn, don't fail the tx:
    if err := q.IncrementRetweetCount(ctx, id); err != nil {
        s.log.Warn("increment retweet count", "err", err)
    }
    // Outbox enqueue is always the last call in the tx:
    return s.outboxEnqueue(ctx, q, events.TopicTweetCreated, result.ID, events.TweetCreatedEvent{...})
}); err != nil {
    return db.Tweet{}, err
}
return result, nil
```

## Naming Conventions

- **Error variables:** always plain `err`. Never `txErr`, `qErr`, `getErr`, `kcErr`.
  Shadow with `:=` in inner scopes — that's idiomatic Go.
- **No type-descriptive suffixes:** never `usernameStr`, `resultOut`, `idPtr`.
  Use `ptr.Deref(s)` or a local `strOrEmpty` helper to unwrap pointers inline.
- **No named returns** unless a closure genuinely needs to capture a result variable.
  Never name the error return `err`.
- **No package name in type name:** `keycloak.Admin` not `keycloak.KeycloakAdmin`.

## JSON Response Rules

- **Never `omitempty` on response struct fields.** All fields serialize as explicit `null`,
  never omitted. Frontend gets a consistent shape regardless of data state.
- **Exception:** `omitempty` in `binding:"..."` tags on *request* types is correct — it controls
  validation, not serialization.
- **Empty collections return `[]`, not `null`.** Initialize slices to `[]T{}` before returning
  from handlers/services so JSON produces `[]` not `null`.
- **Pagination cursors are `*string`** — returns `null` on last page, never omitted.
- **Timestamps are `time.Time`**, never `string`. Let `encoding/json` format RFC3339.
- **Nullable object fields are `*T`** — returns `null` when absent.

## Database / Migrations

- **Never hand-edit `db/sqlc/*.go`** — not to add a query, not to reorder, not to "fix" a type.
  These files are output, not source. Workflow is ALWAYS:
  1. Edit `db/query.sql` (and `db/schema.sql` / migrations if the schema changed).
  2. Run `sqlc generate` (via the project's Makefile target).
  3. Commit both the SQL source and the regenerated `.go` together.
  If `sqlc generate` won't emit what you need, fix `sqlc.yaml` or the SQL — do not patch the
  generated file. Hand-edits silently get blown away on the next regen and make the SQL
  source diverge from runtime behavior.
- **Never create new migration files** for columns on `users` or `tweets` tables.
  Edit the existing initial migration in-place:
  - `apps/user-service/migrations/000001_create_users.up.sql`
  - `apps/tweet-service/migrations/000001_create_tweets.up.sql`

## Best Practices (apply proactively, without being asked)

- **Package cohesion:** each package has one clear responsibility.
- **Shared code belongs in `shared/`:** duplicate logic spotted across services must be moved there.
- **File placement follows project structure:**
  - Infrastructure config → `local/` or `infra/`
  - API docs/collections → `docs/`
  - App code → `apps/`
  Never place files at root level "for now".
- **Research the standard solution first.** Before patching with a workaround, look up the
  idiomatic/official approach. Only fall back to a workaround if the standard approach genuinely
  doesn't apply, and explain why.

## Go Patterns

**Params struct for methods with more than ~3 optional fields:**
```go
type UpdateProfileParams struct {
    Username    *string
    DisplayName *string
    AvatarURL   *string
}
func (s *Service) UpdateProfile(ctx context.Context, userID string, p UpdateProfileParams) error
```

**Interface compile-time check:**
```go
var _ MyInterface = (*Client)(nil)
```

**Concurrency (Go 1.22+/1.25+):**
```go
// No loop variable copy needed (fixed in Go 1.22)
// Use wg.Go() instead of wg.Add(1) + defer wg.Done() (Go 1.25+)
wg.Go(func() { doWork() })
```

**Error comparison:** always `errors.Is`, never `==`.

**Test packages:** use `package foo_test` (external) for black-box tests.

## Architecture / Redis Key Schema

Services share one Redis instance:

```
user:snapshot:{id}    HASH  username, display_name, avatar_url
tweet:snapshot:{id}   HASH  author fields embedded — no second lookup at read time
tweet:counts:{id}     HASH  like_count, retweet_count, reply_count (HINCRBY on write)
author_tweets:{id}    SET   tweet IDs by author (for profile-update propagation)
following:{id}        LIST  fan-out feed
```

- Actor enrichment in **notification-service** reads `user:snapshot` from Redis — no gRPC.
- Feed enrichment reads `tweet:snapshot` + `tweet:counts` from Redis, then one `GetInteractions`
  gRPC call for viewer-specific flags only.
- `GetTweetStats` is gone — replaced by `GetInteractions` (viewer flags) + Redis counts.

## Comments

Default: write **no** comment. Add one only when the WHY is non-obvious.

**Keep:**
- Hidden invariant / ordering constraint (e.g. "Outbox enqueue is always the last call in the tx")
- Idempotency / at-least-once guarantee (e.g. "Redis HSET is idempotent, redelivery is safe")
- Non-obvious fallback / defensive behavior (e.g. "If rdb is nil, fanned out in-process only")
- Critical design decision at odds with the obvious implementation (e.g. "FOR UPDATE SKIP LOCKED")
- Caller usage note not deducible from the signature (e.g. "Cursor sorts on likes.created_at, not tweet creation")

**Remove proactively whenever you touch nearby code:**
- Anything that restates the function/type name (`// GetFoo returns the foo for the given id`)
- Section dividers (`// ── Foo ─────────────────────────────`)
- Phase/task refs (`// Phase 3`, `// added for the Y flow`)
- WHAT introductions before an otherwise-useful WHY sentence — keep the WHY, delete the WHAT lead-in
